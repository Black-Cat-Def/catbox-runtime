# План реферата

**Тема:** Разработка контейнерного рантайма на C++: изоляция процессов
средствами ядра Linux, ограничение ресурсов и мониторинг.

Ориентировочный объём: 20–25 страниц (без приложений).

---

## Введение (1,5–2 стр.)

- Актуальность: контейнеры — стандарт поставки ПО (Kubernetes, CI/CD);
  понимание их внутреннего устройства востребовано у разработчиков и
  DevOps-инженеров.
- Проблема: существующие инструменты (Docker, runc) — «чёрный ящик» для
  изучающего механику контейнеризации.
- Цель работы и задачи (переносим из `docs/01-overview.md`, раздел 5).
- Объект и предмет исследования; методы (системное программирование на C++,
  интерфейсы ядра Linux).

## Глава 1. Обзор технологий контейнеризации (5–6 стр.)

- 1.1. История: chroot → FreeBSD Jails → Solaris Zones → OpenVZ/LXC → Docker
  → OCI (таблица из обзора).
- 1.2. Место рантайма в экосистеме: высокоуровневые (Docker, containerd,
  Podman) vs низкоуровневые (runc, crun, youki); OCI runtime-spec.
- 1.3. Сравнительный анализ существующих рантаймов — таблица:
  язык, размер кодовой базы, соответствие OCI, метрики, особенности
  (runc / crun / youki / LXC / gVisor / Kata).
- 1.4. Выводы по главе: ниша учебного минимального рантайма на C++.

## Глава 2. Механизмы ядра Linux, лежащие в основе контейнеров (6–7 стр.)

- 2.1. Namespaces: виды (mnt, pid, net, uts, ipc, user, cgroup, time),
  системные вызовы `clone`, `unshare`, `setns`, `/proc/<pid>/ns`.
- 2.2. Изоляция файловой системы: `pivot_root`, bind-монтирование,
  минимальный rootfs (busybox), маскировка опасных путей в `/proc`.
- 2.3. cgroups v2: иерархия, контроллеры (cpu, memory, pids, io), лимиты
  (`cpu.max`, `memory.max`, `pids.max`) и метрики (`cpu.stat`,
  `memory.current`, `memory.peak`).
- 2.4. Усиление безопасности: capabilities, seccomp-BPF,
  `no_new_privs`, user namespaces (rootless).
- 2.5. Сетевое устройство контейнера: veth + bridge + NAT; rootless-сети
  (slirp4netns).
- Выводы по главе.

## Глава 3. Проектирование и реализация рантайма (6–7 стр.)

- 3.1. Требования к утилите и интерфейс командной строки
  (`run`, `create`/`start`, `state`, `metrics`, `kill`, `delete`).
- 3.2. Архитектура: процесс-предок (настройка) / процесс-потомок
  (изолированная среда), синхронизация через FIFO/pipe; схема жизненного
  цикла (диаграмма).
- 3.3. Реализация изоляции: создание namespaces флагами `clone(2)`,
  порядок применения (user → mnt → …), обработка ошибок.
- 3.4. Реализация rootfs: подготовка busybox-rootfs, `pivot_root`,
  монтирование `/proc`, размонтирование старого корня.
- 3.5. Реализация лимитов: создание cgroup v2, запись `cpu.max` /
  `memory.max` / `pids.max`, помещение PID в `cgroup.procs`.
- 3.6. Метрики: чтение `cpu.stat`, `memory.current`, `memory.peak`,
  формат вывода (таблица / JSON).
- 3.7. Обработка ошибок и очистка ресурсов (удаление cgroup, временных
  каталогов).
- Выводы по главе.

## Глава 4. Тестирование и оценка (3–4 стр.)

- 4.1. Методика: проверка изоляции (`ps aux`, `ip a`, `hostname` внутри и
  снаружи); проверка лимитов нагрузочными тестами (`stress-ng`,
  fork-бомба против `pids.max`, OOM против `memory.max`).
- 4.2. Результаты: таблица «тест → ожидание → факт».
- 4.3. Сравнение накладных расходов с runc/Docker: время старта контейнера,
  потребление памяти самим рантаймом.
- Выводы по главе.

## Заключение (1–1,5 стр.)

- Что сделано по задачам введения.
- Ограничения работы (одна ОС, частичная OCI-совместимость, без overlayfs).
- Направления развития: полная OCI-совместимость, образы и слои (overlayfs),

   Containerized Applications*. O'Reilly, 2020.
5. Rice L. *Containers From Scratch* (доклад, NGINX Conf 2018).
6. Kerrisk M. Серия статей «Namespaces in operation», LWN.net, 2013.
7. Исходный код: runc (Go), crun (C), youki (Rust) — как референсы.
