## 2. Подробная структура пояснительной записки

### Введение (1,5–2 стр.)
- **Актуальность темы:** Распространение контейнеризации как базового стандарта поставки и изолированного исполнения программного обеспечения; необходимость глубокого понимания механизмов ядра ОС Linux разработчиками системного и серверного ПО.
- **Цель работы:** Исследование принципов низкоуровневой контейнеризации и разработка легковесного консольного рантайма на C++20, обеспечивающего изоляцию процессов, ограничение аппаратных ресурсов и сбор телеметрии.
- **Задачи работы:**
  1. Исследовать архитектуру изоляции процессов в ядре Linux (namespaces, cgroups v2, pivot_root).
  2. Выполнить сравнительный анализ существующих решений (runc, crun, youki, bubblewrap).
  3. Спроектировать двухпроцессную архитектуру рантайма и межпроцессное взаимодействие.
  4. Реализовать программный комплекс на C++20 с декомпозицией на модули изоляции, управления ресурсами и CLI.
  5. Провести тестирование функциональности изоляции и экспериментальную оценку накладных расходов.
- **Объект и предмет исследования:**
  - *Объект:* Технологии контейнеризации и виртуализации на уровне операционной системы.
  - *Предмет:* Системные вызовы ядра Linux, структуры данных и интерфейсы псевдофайловых систем procfs и cgroupfs.
- **Распределение обязанностей в проектной группе:** Описание зон ответственности каждого из трех участников.

### Глава 1. Аналитический обзор технологий контейнеризации (5–6 стр.)
*Ответственный исполнитель: Участник 3*

- **1.1. Эволюция механизмов изоляции в семействе UNIX-подобных ОС:**
  - От примитивов ограничения каталогов (`chroot` в Unix V7) к концепциям изолированных окружений (FreeBSD Jails, Solaris Zones, OpenVZ, LXC).
  - Появление стандартов Open Container Initiative (OCI Image Specification, OCI Runtime Specification).
- **1.2. Архитектура современных сред контейнеризации:**
  - Разграничение высокоуровневых сервисов управления (dockerd, containerd, CRI-O) и низкоуровневых исполнителей (OCI runtime).
  - Спецификация OCI Runtime Spec: структура каталога пакета (`bundle`), схема конфигурации `config.json`, фазы жизненного цикла (`create`, `start`, `kill`, `delete`).
- **1.3. Сравнительный анализ существующих низкоуровневых рантаймов:**
  - `runc` (Go) — эталонная реализация OCI, анализ причин использования вспомогательной прослойки Cgo/nsenter.
  - `crun` (C) — архитектура компактного высокопроизводительного рантайма, работа с cgroups v2.
  - `youki` (Rust) — особенности применения языка с проверкой безопасности памяти.
  - `bubblewrap` (C) — подход к запуску непривилегированных контейнеров без поддержки cgroups.
  - Сводная сравнительная таблица по критериям производительности, объема кодовой базы и поддержки стандартов.
- **1.4. Выводы по главе 1:** Обоснование требований к собственному модульному рантайму на C++20.

### Глава 2. Системные механизмы ядра Linux для изоляции процессов и ресурсов (6–7 стр.)
*Ответственные исполнители: Участник 1 (п. 2.1–2.2), Участник 2 (п. 2.3–2.4), Участник 3 (п. 2.5)*

- **2.1. Механизм пространств имён (Namespaces) (Участник 1):**
  - Принцип действия и назначение типов: `CLONE_NEWNS`, `CLONE_NEWPID`, `CLONE_NEWUTS`, `CLONE_NEWIPC`, `CLONE_NEWNET`, `CLONE_NEWUSER`.
  - Системные вызовы `clone(2)`, `clone3(2)`, `unshare(2)`, `setns(2)`.
  - Структура каталога `/proc/<pid>/ns/` и управление жизненным циклом пространств имён через дескрипторы.
- **2.2. Изоляция файловой системы (Участник 1):**
  - Анализ уязвимостей `chroot(2)` и обоснование использования `pivot_root(2)`.
  - Модель распространения точек монтирования (shared, slave, private mounts) и флаг `MS_PRIVATE`.
  - Монтирование псевдофайловых систем: необходимость отдельного экземпляра `/proc` для корректного отображения дерева процессов PID namespace, монтирование `/dev` (tmpfs).
- **2.3. Контрольные группы cgroups v2 (Участник 2):**
  - Архитектурные отличия cgroups v2 от v1: единая иерархия (unified hierarchy), бесконфликтное распределение контроллеров по поддеревьям.
  - Интерфейс управления через псевдофайловую систему `/sys/fs/cgroup`.
  - Механика контроллеров: ограничение полосы CPU (`cpu.max`), квотирование физической памяти (`memory.max`), защита от fork-бомб (`pids.max`).
- **2.4. Мониторинг и телеметрия контейнеров (Участник 2):**
  - Чтение и парсинг псевдофайлов статистики ядра: `cpu.stat`, `memory.current`, `memory.peak`, `pids.current`.
  - Детектирование событий нехватки памяти (OOM) через `memory.events`.
- **2.5. Модель безопасности и ограничение привилегий (Участник 3):**
  - Модель POSIX capabilities: переход от бинарной модели root/non-root к гранулярным привилегиям.
  - Процедура сброса опасных привилегий (`cap_set_proc`, удаление `CAP_SYS_ADMIN` и др.).
  - Предотвращение эскалации привилегий через механизм `PR_SET_NO_NEW_PRIVS`.
- **Выводы по главе 2.**

### Глава 3. Проектирование и реализация контейнерного рантайма (7–8 стр.)
*Ответственные исполнители: Все участники (по функциональным модулям)*

- **3.1. Требования к системе и архитектурная декомпозиция (Участник 3):**
  - Функциональные требования: запуск команд в rootfs, квотирование ресурсов, сбор телеметрии.
  - Структура CLI-команд: `run`, `stats`, `help`.
  - Модульная архитектура: подсистема изоляции (`isolation`), подсистема ресурсов (`cgroup`), модуль безопасности (`security`), модуль CLI (`cli`).
- **3.2. Модель процессов и синхронизация жизненного цикла (Участник 1):**
  - Двухпроцессная схема: процесс-супервайзер (хостовый контекст) и дочерний init-процесс (контейнерный контекст).
  - Реализация протокола синхронизации через дескриптор канала (pipe) для исключения race conditions (гарантия добавления процесса в cgroup до вызова `execve`).
- **3.3. Реализация подсистемы изоляции (Участник 1):**
  - Алгоритм конфигурирования namespaces флагами системного вызова `clone`.
  - Пошаговая реализация алгоритма смены корня: изоляция дерева монтирования, bind-mount целевого rootfs, вызов `pivot_root`, монтирование `/proc`, отсоединение и размонтирование старого корня.
- **3.4. Реализация управления ресурсами и мониторинга (Участник 2):**
  - Класс управления cgroup на базе RAII: гарантированное создание и рекурсивное удаление узла при завершении процесса.
  - Запись лимитов и добавление PID в `cgroup.procs`.
  - Реализация фонового сбора метрик и форматирования вывода для пользователя.
- **3.5. Реализация модели безопасности (Участник 3):**
  - Программный интерфейс сброса capabilities через библиотеку `libcap`.
  - Установка флага `PR_SET_NO_NEW_PRIVS`.
- **Выводы по главе 3.**

### Глава 4. Экспериментальные исследования и тестирование (4–5 стр.)
*Ответственные исполнители: Участник 3, Участник 2*

- **4.1. Методика тестирования:**
  - Тестовый стенд: конфигурация аппаратного обеспечения, версия ядра Linux, используемый дистрибутив и тестовый rootfs (`busybox`).
  - План верификации изоляции: проверка изоляции PID (внутри контейнера первый процесс имеет PID 1), изоляции монтирования, сетевого интерфейса и имени хоста.
- **4.2. Результаты функционального тестирования изоляции (Участник 3):**
  - Таблица результатов проверок (тест, ожидаемый результат, фактический результат).
  - Скриншоты и логи выполнения проверочных команд (`ps aux`, `cat /proc/mounts`, `hostname`).
- **4.3. Нагрузочное тестирование ограничений cgroups v2 (Участник 2):**
  - Тестирование лимита памяти: запуск процесса с выделением памяти сверх лимита, регистрация OOM-kill в `memory.events`.
  - Тестирование лимита CPU: замер утилизации процессора при синтетической нагрузке через `stress-ng`.
  - Тестирование лимита процессов: запуск fork-бомбы, фиксация блокировки создания потоков по достижению `pids.max`.
- **4.4. Сравнительный анализ накладных расходов с runc (Участник 3):**
  - Замер времени «холодного старта» контейнера (от вызова команды до вызова entrypoint).
  - Замер потребления оперативной памяти супервайзером рантайма.
  - Анализ причин различий в производительности (C++20 vs Go runtime).
- **Выводы по главе 4.**
