# Обзор предметной области

> Документ отвечает на общие вопросы о проекте: для чего нужна контейнеризация,
> чего не хватает существующим решениям, как контейнеры устроены внутри и
> какую нишу занимает наш проект.

## 1. Для чего это нужно?

Контейнеризация решает несколько фундаментальных проблем разработки и
эксплуатации ПО:

1. **Воспроизводимость окружения.** Классическая проблема «у меня на машине
   работает»: приложение зависит от версий библиотек, переменных окружения,
   системных пакетов. Контейнер упаковывает приложение вместе со всем
   окружением, и оно ведёт себя одинаково на ноутбуке разработчика, в CI и в
   продакшене.

2. **Изоляция.** Процессы внутри контейнера не видят чужие процессы, файлы и
   сетевые интерфейсы. Это основа multi-tenant систем, CI-раннеров и запуска
   недоверенного кода.

3. **Управление ресурсами.** Можно жёстко ограничить CPU и память контейнера,
   гарантировать качество обслуживания (QoS) и защититься от «шумного соседа»,
   который съест все ресурсы машины.

4. **Плотность и скорость.** В отличие от виртуальной машины, контейнер не
   запускает отдельное ядро ОС: старт занимает миллисекунды (против десятков
   секунд у VM), накладные расходы близки к нулю, на одном хосте помещаются
   сотни контейнеров там, где поместилось бы десять VM.

5. **Стандарт поставки ПО.** Микросервисная архитектура, CI/CD и оркестраторы
   (Kubernetes) построены вокруг контейнера как единицы развёртывания.
   Формат стандартизован Open Container Initiative (OCI).

### Краткая история

| Год | Технология | Вклад |
|-----|-----------|-------|
| 1979 | `chroot` (Unix V7) | первая изоляция файловой системы |
| 2000 | FreeBSD Jails | изоляция FS + сети + процессов |
| 2004 | Solaris Zones | доведённая до ума OS-виртуализация |
| 2005 | OpenVZ | контейнеры на патченом ядре Linux |
| 2007–2008 | cgroups в ядре (Google), LXC | контейнеры в мейнлайн-ядре Linux |
| 2013 | Docker | образы, слои, registry — контейнеры «для людей» |
| 2015 | OCI, runc | стандартизация; Docker отделил низкоуровневый рантайм |
| 2017+ | containerd, CRI-O, Podman; crun (C), youki (Rust) | зрелая экосистема рантаймов |
| 2018+ | gVisor, Kata Containers, Firecracker | sandbox-рантаймы с усиленной изоляцией |

## 2. Чего не хватает существующим решениям?

Честный ответ: **для продакшена — почти ничего**. runc/crun — де-факто
стандарт, написание «своего Docker для прода» бессмысленно. Ценность нашего
проекта лежит в других плоскостях.

### 2.1. Образовательный дефицит

Все существующие решения — «чёрный ящик» для изучающего тему:

- **Docker** прячет всю механику за демоном, REST API и слоями абстракций
  (dockerd → containerd → containerd-shim → runc). Понять по Docker'у, что
  контейнер — это не магия, а набор из нескольких механизмов ядра, невозможно.
- **runc** — эталонная реализация OCI, но это ~15 тыс. строк Go, написанных
  строго под спецификацию. Читать его без подготовки тяжело.
- **crun** (C) и **youki** (Rust) — те же задачи в других языках, та же
  сложность входа.

При этом известные учебные материалы (доклад Лиз Райс «Containers From
Scratch» и др.) показывают: чтобы понять контейнер, его надо **написать
самому** — это ~несколько сотен строк кода в минимальном виде. Именно этот
путь мы и проходим.

### 2.2. Технические недостатки существующих инструментов

- **Docker** — монолитный демон, работающий от root (большая поверхность
  атаки); тянет управление образами, сетями, томами, сборкой — избыточен для
  задачи «запустить один процесс изолированно».
- **runc** — только создаёт и запускает контейнер по готовому OCI-bundle:
  нет метрик «из коробки», минималистичный UX, всё сопутствующее (образы,
  сеть) оставлено вышележащим слоям.
- **LXC / systemd-nspawn** — «системные» контейнеры с полноценным init
  внутри; другая ниша, другие компромиссы.
- **gVisor / Kata / Firecracker** — усиленная изоляция через перехват
  системных вызовов или микро-VM. Они показывают, что «одного рантайма на все
  случаи» не существует: каждый выбирает свою точку компромисса между
  безопасностью, производительностью и совместимостью.

### 2.3. Практическая ниша

Минимальные специализированные рантаймы реально востребованы там, где тащить
containerd нельзя: встраиваемые и edge-устройства, sandbox для запуска
приложений (как bubblewrap у Flatpak), CI-агенты. Рантайм в несколько сотен
строк C++ можно **полностью проаудировать**, чего не скажешь о миллионах строк
экосистемы Docker.

### Вывод раздела

Наш рантайм — не конкурент runc, а:
1. учебный разбор механики контейнеров «с нуля» на системном языке;
2. минимальный, целиком аудируемый рантайм с лимитами ресурсов и метриками.

C++ выбран осознанно: отсутствие GC и рантайм-накладных расходов, прямой
доступ к системным вызовам (`clone(2)`, `unshare(2)`, `pivot_root(2)`) и
актуальность языка в системном ПО.

## 3. Как это устроено внутри: механизмы ядра Linux

Контейнер — это обычный процесс Linux, к которому применён набор механизмов
ядра. Ничего другого в контейнере нет.

### 3.1. Namespaces — изоляция «видимости»

Создаются флагами к `clone(2)`/`unshare(2)`, подключение к существующим —
`setns(2)`, посмотреть можно в `/proc/<pid>/ns/`:

| Namespace | Флаг | Что изолирует |
|-----------|------|----------------|
| Mount | `CLONE_NEWNS` | таблицу монтирования (своя файловая система) |
| PID | `CLONE_NEWPID` | дерево процессов (внутри свой PID 1) |
| Network | `CLONE_NEWNET` | сетевой стек: интерфейсы, таблицы маршрутизации |
| UTS | `CLONE_NEWUTS` | hostname и domainname |
| IPC | `CLONE_NEWIPC` | SysV IPC, очереди сообщений POSIX |
| User | `CLONE_NEWUSER` | отображение UID/GID (основа rootless-контейнеров) |
| Cgroup | `CLONE_NEWCGROUP` | вид на иерархию cgroups |
| Time | `CLONE_NEWTIME` | монотонные часы (boottime) |

### 3.2. Файловая система

- `pivot_root(2)` (не `chroot` — тот обходится тривиально) подменяет корень
  процесса на подготовленный rootfs;
- минимальный rootfs собирается из статического `busybox`;
- `/proc` монтируется внутри для работы утилит;
- `overlayfs` позволяет слои «нижний read-only образ + верхний слой записи»
  (перспектива, уровень v0.4);
- маскировка опасных путей (`/proc/kcore`, `/proc/sysrq-trigger` и т. п.).

### 3.3. cgroups v2 — ограничение ресурсов и метрики

Контейнер помещается в свою cgroup, лимиты задаются записью в cgroupfs:

| Файл | Назначение |
|------|-----------|
| `cpu.max` | квота CPU (`quota period`, например `50000 100000` = 50% ядра) |
| `memory.max` | жёсткий лимит памяти (превышение → OOM-kill) |
| `memory.swap.max` | лимит подкачки |
| `pids.max` | защита от fork-бомб |
| `io.max` | лимиты блочного ввода-вывода |

Метрики читаются оттуда же: `cpu.stat` (usage_usec, user/system),
`memory.current`, `memory.peak`, `memory.events` (OOM-события), `pids.current`.

### 3.4. Безопасность

- **capabilities(7)**: вместо полного root контейнеру оставляют подмножество
  (например, забирают `CAP_SYS_ADMIN`, `CAP_SYS_MODULE`);
- **seccomp-BPF(2)**: фильтрация доступных системных вызовов;
- `PR_SET_NO_NEW_PRIVS`: запрет эскалации привилегий через setuid-бинарники;
- user namespaces: root внутри контейнера — непривилегированный пользователь
  снаружи.

### 3.5. Сеть (этап v0.3)

По умолчанию контейнер получает пустой сетевой namespace (только loopback).
Варианты: пара `veth` + bridge на хосте + NAT; rootless-вариант через
`slirp4netns`/`pasta`.

### 3.6. Жизненный цикл (по мотивам OCI runtime-spec)

```
create  →  процесс-предок создаёт namespaces, child блокируется на FIFO
start   →  предок пишет в FIFO, child делает pivot_root, drop caps, exec
running →  контейнер работает, рантайм читает метрики из cgroupfs
stopped →  предок собирает код возврата, удаляет cgroup
```

## 4. Стандарт OCI

Open Container Initiative стандартизировала формат образа (image-spec) и
поведение рантайма (runtime-spec: `config.json`, состояния, хуки). Ориентир
зрелости для нашего проекта — принять на вход OCI-совместимый `config.json`
(v0.4); это позволит сравниваться с runc «на его же поле».

## 5. Постановка проекта

**Цель:** разработать на C++ легковесную CLI-утилиту — контейнерный рантайм
для Linux, запускающий приложение в изолированном окружении (namespaces),
ограничивающий потребление CPU и памяти (cgroups v2) и предоставляющий
метрики работы контейнера.

**Задачи:**

1. Изучить механизмы изоляции ядра Linux: namespaces, cgroups v2,
   capabilities, seccomp, `pivot_root`.
2. Провести сравнительный анализ существующих рантаймов (runc, crun, youki,
   LXC, gVisor, Kata Containers).
3. Спроектировать архитектуру утилиты и интерфейс командной строки.
4. Реализовать:
   - создание изолированных namespaces;
   - подготовку и подключение собственного rootfs через `pivot_root`;
   - ограничение ресурсов через cgroups v2;
   - сбор и вывод метрик (CPU, память, PIDs).
5. Провести тестирование: проверка изоляции (`ps`, `ip`, `hostname` внутри
   контейнера), проверка лимитов (нагрузочные тесты), сравнение накладных
   расходов с runc и Docker.
