# Аналитический обзор предметной области и техническое задание

Данный документ содержит аналитический обзор технологий низкоуровневой контейнеризации в ОС Linux, исследование системных интерфейсов ядра, анализ существующих решений и архитектурное техническое задание на разработку курсового проекта.

---

## 1. Введение и архитектурный контекст

В современной IT-инфраструктуре контейнеризация уровня операционной системы является ключевой технологией изолированного развертывания приложений. В отличие от аппаратной виртуализации (гипервизоры Type-1 и Type-2), виртуализация уровня ОС не эмулирует виртуальное оборудование и не запускает отдельный экземпляр ядра для каждого гостевого окружения. Все контейнеры разделяют единое ядро хостовой операционной системы, а изоляция достигается за счет встроенных механизмов разграничения видимости и квотирования ресурсов ядра Linux.

Экосистема контейнеризации делится на два основных уровня:

1. **Высокоуровневые среды выполнения (High-level runtimes):** `Docker` (`dockerd`), `containerd`, `CRI-O`, `Podman`. Они отвечают за сетевое взаимодействие кластера, управление образами (pull/push из OCI Registry), распаковку слоев файловой системы, управление томами данных и интеграцию с API Kubernetes (CRI).
2. **Низкоуровневые среды выполнения (Low-level / OCI runtimes):** `runc`, `crun`, `youki`. Они непосредственно взаимодействуют с ядром ОС: настраивают пространства имён (namespaces), монтируют изолированную файловую систему (`rootfs`), конфигурируют контрольные группы (`cgroups`), понижают привилегии процесса и вызывают `execve` для запуска полезной нагрузки.

Целью данного курсового проекта является разработка низкоуровневого рантайма на языке C++20, исключающего громоздкие промежуточные демоны и раскрывающего механизмы ядра Linux «из первых принципов».

## 2. Анализ существующих решений

Для формирования требований к разрабатываемому рантайму выполнен сравнительный анализ существующих реализаций низкоуровневой изоляции:

| Критерий | `runc` | `crun` | `youki` | `bubblewrap` | Проектируемый рантайм |
|---|---|---|---|---|---|
| **Язык разработки** | Go (с Cgo-модулями) | C | Rust | C | C++20 |
| **Размер кодовой базы** | ~40k строк кода | ~30k строк кода | ~25k строк кода | ~5k строк кода | < 2k строк кода (минималистичный) |
| **Runtime / GC оверхед** | Присутствует (Go runtime) | Отсутствует | Отсутствует | Отсутствует | Отсутствует |
| **Время запуска (cold start)** | Среднее (~15–25 мс) | Минимальное (~2–5 мс) | Низкое (~5–10 мс) | Минимальное (~2–4 мс) | Минимальное (< 5 мс) |
| **Иерархия cgroups** | v1 / v2 | v1 / v2 | v1 / v2 | Не поддерживается | Исключительно v2 (unified) |
| **Поддержка OCI runtime-spec** | Полная (эталонная) | Полная | Полная | Частичная / специфичная | Базовое подмножество |
| **Основное назначение** | Стандарт индустрии (Docker, K8s) | Высокопроизводительный OCI | Альтернатива на безопасном Rust | Непривилегированные песочницы (Flatpak) | Учебный анализ и профилирование системных вызовов |

### Особенности существующих аналогов:
- **`runc`**: Реализован на Go, из-за чего вынужден использовать вспомогательный модуль на Си (`nsenter/nsexec.c`), так как многопоточный планировщик Go не позволяет безопасно вызывать системный вызов `setns(2)` после старта горутин.
- **`crun`**: Разработан на чистом Си Red Hat для снижения задержек и экономии памяти в средах с высокой плотностью контейнеров. Является хорошим примером прямой работы с cgroups v2 и Linux syscalls.
- **`bubblewrap`**: Сфокусирован на непривилегированном запуске пользовательских программ с помощью User Namespaces, не реализует управление ресурсами (cgroups).

**Выбор языка C++20 для курсового проекта обусловлен:**
1. Прямым доступом к системным интерфейсам Linux (POSIX API, `syscall(2)`).
2. Отсутствием непредсказуемых пауз сборщика мусора (GC) и накладных расходов фонового рантайма.
3. Возможностью применения современных идиом C++ (RAII для автоматического освобождения дескрипторов и ресурсов, строгая типизация, `std::filesystem`, `std::expected` / исключения для обработки системных ошибок).

## 3. Системные механизмы изоляции в ядре Linux

Контейнер в Linux не является отдельной аппаратной сущностью — это обычный процесс, изоляция которого обеспечивается комбинацией механизмов ядра.

### 3.1. Пространства имён (Namespaces)

Namespaces разграничивают видимость глобальных системных ресурсов для группы процессов.

| Пространство имён | Флаг системного вызова | Изолируемый системный ресурс |
|---|---|---|
| **Mount (mnt)** | `CLONE_NEWNS` | Таблица точек монтирования файловой системы |
| **PID** | `CLONE_NEWPID` | Дерево процессов (первый процесс становится PID 1 внутри окружения) |
| **Network (net)** | `CLONE_NEWNET` | Сетевые интерфейсы, таблицы маршрутизации, сокеты, правила фильтрации |
| **UTS** | `CLONE_NEWUTS` | Имя хоста (`hostname`) и доменное имя (`domainname`) |
| **IPC** | `CLONE_NEWIPC` | Очереди сообщений POSIX/SysV, семафоры и разделяемая память |
| **User (user)** | `CLONE_NEWUSER` | Таблицы отображения UID/GID (root внутри контейнера отображается в непривилегированного пользователя на хосте) |
| **Cgroup** | `CLONE_NEWCGROUP` | Виртуализированное представление иерархии `/proc/self/cgroup` |

Для создания пространств имён используются системные вызовы `clone(2)` (создание нового дочернего процесса сразу в новых пространствах) либо `unshare(2)` (отделение вызывающего процесса от текущих пространств имён хоста).

### 3.2. Изоляция файловой системы и `pivot_root`

Использование устаревшего системного вызова `chroot(2)` небезопасно, так как привилегированный процесс может выйти за пределы изоляции через относительные пути или сохранённые файловые дескрипторы корневого каталога.

В проектируемом рантайме применяется механизм `pivot_root(2)`:
1. Текущее дерево монтирования переводится в приватный режим распространения (`mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL)`), чтобы операции внутри контейнера не распространялись на хостовую систему.
2. Целевой каталог rootfs монтируется как bind-mount сам на себя для превращения его в полноценную точку монтирования (`MS_BIND | MS_REC`).
3. Вызывается `pivot_root(new_root, put_old)`, меняющий корень файловой системы вызывающего процесса.
4. Старый корневой каталог размонтируется с помощью `umount2(old_root, MNT_DETACH)`.
5. Внутри изолированного окружения монтируются псевдофайловые системы:
   - `/proc` (тип `proc`, флаги `MS_NOSUID | MS_NODEV | MS_NOEXEC`) — необходима для функционирования утилит мониторинга (`ps`, `top`);
   - `/dev` (тип `tmpfs` с созданием минимального набора символьных устройств: `null`, `zero`, `urandom`).

### 3.3. Управление ресурсами: контрольные группы cgroups v2

В проекте используется исключительно унифицированная иерархия cgroups v2 (unified hierarchy, монтируемая в `/sys/fs/cgroup`), устраняющая фрагментацию и конфликты между независимыми контроллерами cgroups v1.

Контроль ресурсов осуществляется через запись значений в управляющие псевдофайлы в соответствующем подкаталоге:
- **CPU (`cpu.max`):** Ограничение полосы процессорного времени в формате `$QUOTA $PERIOD` (в микросекундах). Например, значение `50000 100000` ограничивает процесс 50% одного процессорного ядра.
- **Память (`memory.max`):** Жёсткий лимит потребления оперативной памяти в байтах. При превышении ядро вызывает OOM Killer для процессов внутри cgroup.
- **Число процессов (`pids.max`):** Максимальное количество активных задач (нитей и процессов), предотвращающее отказ в обслуживании хоста (fork-бомбы).

Сбор телеметрии выполняется посредством чтения файлов состояния ядра:
- `cpu.stat`: общее время работы в user/system пространстве (`usage_usec`);
- `memory.current`: текущий объем используемой физической памяти;
- `memory.peak`: пиковое значение потребления RAM за время жизни контейнера;
- `memory.events`: количество срабатываний механизма OOM (`oom`, `oom_kill`);
- `pids.current`: текущее количество активных процессов внутри cgroup.

### 3.4. Модель безопасности

Для минимизации поверхности атаки на хостовое ядро реализуются базовые принципы эшелонированной защиты:
1. **Сброс POSIX Capabilities (`cap_set_proc`):** Ограничение прав суперпользователя внутри контейнера (изъятие `CAP_SYS_ADMIN`, `CAP_SYS_MODULE`, `CAP_SYS_RAWIO`).
2. **Флаг `PR_SET_NO_NEW_PRIVS`:** Вызов `prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)` запрещает дочерним процессам повышать свои привилегии через бинарные файлы с установленным битом `setuid`/`setgid`.

## 4. Архитектура проектируемого рантайма

Рантайм строится по двухпроцессной модели с синхронизацией через IPC (Unix domain socketpair или анонимный pipe):

```
+-------------------------------------------------------------+
| Родительский процесс (Supervisor)                           |
| 1. Читает CLI-параметры (лимиты, путь к rootfs, команда)    |
| 2. Создает директорию cgroup (/sys/fs/cgroup/runtime/<id>)  |
| 3. Записывает лимиты в cpu.max, memory.max, pids.max        |
| 4. Вызывает clone(..., SIGCHLD | CLONE_NEWPID | ...)        |
| 5. Записывает PID потомка в /sys/fs/cgroup/.../cgroup.procs |
| 6. Отправляет байт готовности потомку по IPC-каналу         |
| 7. Опрашивает метрики / ожидает завершения (waitpid)        |
| 8. Удаляет cgroup при завершении                            |
+-------------------------------------------------------------+
                              │
                    Синхронизация (IPC)
                              │
                              ▼
+-------------------------------------------------------------+
| Дочерний процесс (Container Init)                           |
| 1. Блокируется на чтении из IPC до настройки cgroup         |
| 2. Настраивает mount-изоляцию (MS_PRIVATE, bind-mount)      |
| 3. Вызывает pivot_root и очищает старый корень              |
| 4. Монтирует виртуальные ФС (/proc, /dev)                   |
| 5. Применяет политику безопасности (cap_set_proc, no_privs) |
| 6. Вызывает execve() целевого процесса                      |
+-------------------------------------------------------------+
```

Такая модель устраняет состояние гонки (race condition), гарантируя, что контейнерный процесс не начнет исполнение пользовательского кода до тех пор, пока родительский процесс не зафиксирует его в контрольной группе с примененными лимитами.

## 5. Техническое задание и распределение задач в команде

### 5.1. Требования к разрабатываемому ПО
1. Запуск изолированного процесса командой вида:
   ```bash
   ./catbox run --rootfs /path/to/rootfs --memory 128M --cpus 0.5 --max-pids 64 /bin/sh
   ```
2. Поддержка вывода телеметрии работающего контейнера:
   ```bash
   ./catbox stats <container-id>
   ```
3. Гарантированное завершение и освобождение занятых ресурсов (удаление cgroup, размонтирование временных точек) даже при аварийном завершении полезной нагрузки.
