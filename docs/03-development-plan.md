# План и этапы разработки продукта (Development Plan)

Документ описывает производственный процесс разработки легковесного контейнерного рантайма на C++20 командой из 3 человек. Процесс выстроен по гибкой итеративной модели (Agile/Scrum-подобные спринты) с четким разделением продуктовых и инженерных зон ответственности.

---

## 1. Продуктовые и инженерные роли в команде

| Участник | Продуктовая роль | Инженерная роль | Основные обязанности |
|---|---|---|---|
| **Участник 1** | **Product Manager (PM) / Team Lead** | **Lead Core Developer** | • Формирование требований к продукту (SRS / Product Backlog).<br>• Архитектурный контроль и согласование интерфейсов подсистем.<br>• Разработка ядра: процессная модель (`clone`/`unshare`), синхронизация родителя и потомка, смена корня (`pivot_root`), монтирование `/proc` и `/dev`.<br>• Координация этапов сдачи проекта и защита курсовой работы. |
| **Участник 2** | **DevOps / System Administrator** | **Systems & Metrics Developer** | • Подготовка и сопровождение инфраструктуры разработки (Linux ядро ≥ 5.8, cgroups v2).<br>• Подготовка минимальных тестовых образов rootfs (`busybox`, `alpine`).<br>• Разработка подсистемы cgroups v2: квотирование памяти (`memory.max`), CPU (`cpu.max`), процессов (`pids.max`).<br>• Реализация сбора телеметрии и мониторинга ресурсов в реальном времени. |
| **Участник 3** | **QA Lead / Security Specialist** | **CLI & Security Developer** | • Разработка стратегии и плана тестирования (Test Plan & Test Cases).<br>• Проектирование и реализация интерфейса командной строки (CLI UX: парсинг флагов, валидация входных данных).<br>• Реализация подсистемы безопасности: сброс capabilities (`libcap`), установка флага `PR_SET_NO_NEW_PRIVS`.<br>• Автоматизация функциональных и нагрузочных тестов, проведение сравнительных бенчмарков с `runc`. |

## 2. Этапы и график разработки (Спринты)

Длительность проекта разбита на 4 ключевых этапа (спринта), каждый из которых завершается поставкой рабочего инкремента продукта.

```
[Этап 1: Архитектурный каркас и Core MVP]
       │
       ▼
[Этап 2: Управление ресурсами и телеметрия (cgroups v2)]
       │
       ▼
[Этап 3: Безопасность (Hardening) и доработка CLI]
       │
       ▼
[Этап 4: Комплексный QA, бенчмаркинг и релиз]
```

---

### Спринт 1. Архитектурный каркас и базовый прототип изоляции (Core MVP)
**Цель спринта:** Реализовать запуск процесса в изолированных пространствах имён с собственной файловой системой на базе `busybox`.

* **Задачи по ролям:**
  * **PM / Lead Dev (Участник 1):**
    - Спроектировать структуру проекта и межмодульные интерфейсы (`include/`).
    - Реализовать системный вызов `clone` с флагами `CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC`.
    - Реализовать изоляцию файловой системы: перевод дерева монтирования в `MS_PRIVATE`, bind-mount целевого rootfs, вызов `pivot_root`, монтирование `/proc` и очистку старого корня.
    - Реализовать синхронизацию родительского и дочернего процессов через анонимный канал (pipe).
  * **DevOps / SysAdmin (Участник 2):**
    - Развернуть тестовое окружение на Linux с включённой иерархией cgroups v2.
    - Собрать и настроить минимальный rootfs на базе `busybox` и `alpine-minirootfs`.
    - Настроить базовую конфигурацию CMake для сборки C++20 с поддержкой санитайзеров (ASan, UBSan).
  * **QA / Security (Участник 3):**
    - Реализовать первичный CLI-парсер базовых аргументов: `--rootfs <path>` и целевая команда с аргументами.
    - Составить тест-кейсы для проверки базовой изоляции: проверка смены hostname внутри окружения, проверка дерева процессов (`ps aux` показывает PID 1).
* **Критерии готовности (DoD):**
  - Утилита успешно запускает `/bin/sh` внутри изолированного каталога rootfs.
  - Изменение имени хоста внутри контейнера не затрагивает хостовую систему.
  - Дерево процессов изолировано: процессы хоста не видны внутри контейнера.

---

### Спринт 2. Ограничение ресурсов и мониторинг (cgroups v2 & Metrics)
**Цель спринта:** Реализовать контроль выделяемых ресурсов и сбор телеметрии работы контейнера в реальном времени.

* **Задачи по ролям:**
  * **DevOps / SysAdmin (Участник 2):**
    - Спроектировать RAII-класс для управления cgroup-скоупом (`/sys/fs/cgroup/catbox/<id>`).
    - Реализовать применение лимитов через запись в cgroupfs:
      - память: `memory.max`;
      - процессор: `cpu.max` (пересчёт долей ядер в квоты микросекунд);
      - количество процессов: `pids.max`.
    - Реализовать сбор метрик: чтение и парсинг файлов `cpu.stat`, `memory.current`, `memory.peak`, `pids.current`.
    - Гарантировать корректное рекурсивное удаление cgroup при выходе из контейнера.
  * **PM / Lead Dev (Участник 1):**
    - Интегрировать связку родительского процесса с подсистемой cgroups: запись PID дочернего процесса в `cgroup.procs` до отправки сигнала на запуск `execve`.
    - Реализовать механизм обработки сигналов завершения (SIGINT, SIGTERM, SIGCHLD) и сбор кода возврата через `waitpid`.
  * **QA / Security (Участник 3):**
    - Добавить CLI-аргументы лимитов: `--memory <size>`, `--cpus <ratio>`, `--max-pids <count>`.
    - Реализовать подкоманду `stats <container-id>` (вывод текущей телеметрии в читаемом виде и в формате JSON).
    - Разработать нагрузочные тесты с использованием `stress-ng` для верификации срабатывания лимитов памяти и CPU.
* **Критерии готовности (DoD):**
  - При превышении лимита памяти процесс контейнера завершается OOM-киллером ядра, событие фиксируется в метриках.
  - Лимит `pids.max` успешно блокирует попытки размножения процессов (fork-бомба локализуется).
  - Команда `stats` корректно отображает использование CPU и памяти запущенным контейнером.

### Спринт 3. Безопасность и доработка интерфейса (Security & UX)
**Цель спринта:** Усилить изоляцию контейнера, ограничить привилегии и финализировать интерфейс командной строки.

* **Задачи по ролям:**
  * **QA / Security (Участник 3):**
    - Реализовать модуль сброса опасных привилегий POSIX capabilities с помощью `libcap`: изъятие `CAP_SYS_ADMIN`, `CAP_SYS_MODULE`, `CAP_SYS_RAWIO` и др.
    - Включить защиту от повышения привилегий через вызов `prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)`.
    - Реализовать валидацию всех входных путей, проверку прав суперпользователя на старте и понятные сообщения об ошибках (error handling).
  * **PM / Lead Dev (Участник 1):**
    - Реализовать безопасное монтирование `/dev` с минимальным набором устройств (`null`, `zero`, `urandom`).
    - Маскирование потенциально опасных путей в `/proc` (например, `/proc/sysrq-trigger`, `/proc/kcore`).
    - Рефакторинг модуля процессов: обработка аварийных ситуаций, гарантия очистки ресурсов.
  * **DevOps / SysAdmin (Участник 2):**
    - Реализовать поддержку монтирования tmpfs в `/tmp` внутри контейнера.
    - Проверить стабильность очистки cgroups и точек монтирования при непредвиденном завершении утилиты (`kill -9`).
    - Подготовить скрипты автоматической инициализации окружения для команды и проверяющих преподавателей.
* **Критерии готовности (DoD):**
  - Запуск SUID-бинарников внутри контейнера не позволяет повысить привилегии на хосте.
  - Привилегии root внутри контейнера ограничены: запрещена загрузка модулей ядра и прямое обращение к оборудованию.
  - При любом сценарии завершения (штатном или по ошибке) за собой не остается «висячих» cgroup и маунтов.

### Спринт 4. Комплексное тестирование, бенчмаркинг и релиз (QA, Benchmarks & Release)
**Цель спринта:** Провести полный цикл приёмочных испытаний, замерить накладные расходы относительно `runc`, подготовить проектную документацию и дистрибутив.

* **Задачи по ролям:**
  * **QA / Security (Участник 3):**
    - Сформировать автоматизированный тестовый набор (`tests/isolation_test.sh`, `tests/resource_test.sh`).
    - Разработать скрипт бенчмаркинга (`tests/benchmark.py`): замер времени «холодного старта» и потребления RAM в сравнении с `runc`.
    - Составить матрицу результатов тестирования («Тест — Ожидание — Факт») для включения в отчет.
  * **DevOps / SysAdmin (Участник 2):**
    - Сформировать релизный архив с бинарником, инструкциями и тестовым образом rootfs.
    - Оформить инструкции по сборке и системным зависимостям для различных дистрибутивов Linux (Ubuntu/Debian, Fedora, Arch).
  * **PM / Lead Dev (Участник 1):**
    - Провести интеграционное ревью кода (Code Review), устранить предупреждения компилятора и линтеров.
    - Финализировать текст пояснительной записки (реферата), собрать материалы от всех участников.
    - Подготовить презентацию проекта и демонстрационный сценарий для защиты.
* **Критерии готовности (DoD):**
  - Все функциональные и стресс-тесты проходят без ошибок.
  - Получены количественные графики/таблицы сравнения производительности с `runc`.
  - Пояснительная записка оформлена и согласована всеми участниками команды.

## 3. Матрица рисков проекта и меры по их предотвращению

| Риск | Вероятность / Влияние | Меры по предотвращению (Митигация) | Ответственный |
|---|---|---|---|
| **Утечка cgroup или точек монтирования при падении** | Средняя / Высокая | Использование RAII-оберток в C++, регистрация обработчиков сигналов (`sigaction`) для принудительной очистки перед выходом. | Участник 1, Участник 2 |
| **Несовместимость с версиями cgroups (v1 vs v2)** | Средняя / Средняя | Валидация файловой системы `/sys/fs/cgroup` на старте утилиты; явный вывод понятной ошибки при отсутствии cgroups v2 unified hierarchy. | Участник 2 |
| **Race condition при добавлении PID в cgroup** | Высокая / Высокая | Синхронизация через блокирующее чтение из pipe: дочерний процесс ждет байт подтверждения от родителя перед вызовом `execve`. | Участник 1 |
| **Ошибки безопасности при pivot_root** | Средняя / Высокая | Строгое соблюдение спецификации: перевод корня в `MS_PRIVATE`, bind-mount rootfs, размонтирование старого корня с `MNT_DETACH`. | Участник 1, Участник 3 |
| **Срыв сроков сдачи этапов** | Средняя / Высокая | Фиксация еженедельных контрольных точек (синхронизаций), четкие критерии DoD для каждого спринта. | Участник 1 (PM) |
